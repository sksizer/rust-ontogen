Generated CRUD covers the standard five operations: list, get, create, update, delete. But real applications need more -- bulk operations, filtered queries, aggregations, business logic endpoints. Ontogen handles this by scanning your hand-written API modules and merging them into the same pipeline as generated code.

The result: your custom endpoints show up in Axum routes, Tauri IPC commands, and MCP tools automatically. No extra wiring.

## How it works

`gen_api()` does two things:

1. Generates CRUD modules from entity definitions (written to `generated/`).
2. Scans directories you specify for hand-written modules (parsed with `syn`).

Both types are normalized into the same `ApiModule` / `ApiFnMeta` types. Downstream generators (servers, clients) see no difference between generated and custom endpoints.

The scan happens at build time. When you add a new `.rs` file to a scan directory, the next `cargo build` picks it up.

## Recipe: Add a custom endpoint

<Steps>

1. ### Create the module file

   Put your custom endpoint in the API directory alongside the `generated/` subdirectory. For example, if your generated CRUD for workouts lives at `src/api/v1/generated/workout.rs`, create a custom module at `src/api/v1/workout_stats.rs`:

   ```rust
   // src/api/v1/workout_stats.rs

   use crate::schema::{AppError, Workout};
   use crate::store::Store;

   /// Get the total number of workouts in the last 30 days
   pub async fn recent_count(store: &Store) -> Result<i64, AppError> {
       store.count_recent_workouts(30).await
   }

   /// Get the heaviest workout set across all exercises
   pub async fn personal_best(
       store: &Store,
       exercise_id: &str,
   ) -> Result<Option<Workout>, AppError> {
       store.get_personal_best(exercise_id).await
   }
   ```

   Two things matter here:

   - **First parameter type**: the scanner checks whether the first parameter is your `AppState` type or your `Store` type (as configured in `ApiConfig`). This determines scoping -- `Store`-scoped functions get entity routes, `AppState`-scoped functions get app-level routes.
   - **Doc comments**: the `///` comments become the `doc` field in `ApiFnMeta`. MCP tools use this as the tool description. Future OpenAPI generation will use it too. Write useful descriptions.

2. ### Register in `mod.rs`

   Add the module to your API directory's `mod.rs`:

   ```rust
   // src/api/v1/mod.rs
   pub mod generated;
   pub mod workout_stats;  // your custom module
   ```

3. ### Configure scan directories

   Make sure your `ApiConfig` includes the directory to scan:

   ```rust
   let api = gen_api(&schema.entities, &ApiConfig {
       output_dir: "src/api/v1/generated".into(),
       exclude: vec![],
       scan_dirs: vec!["src/api/v1".into()],  // scans for hand-written modules
       state_type: "AppState".to_string(),
       store_type: Some("Store".to_string()),
       schema_module_path: ontogen::DEFAULT_SCHEMA_MODULE_PATH.into(),
   })?;
   ```

   With the [`Pipeline`](/concepts/pipeline/) builder, this is `.api("src/api/v1/generated", "AppState").api_scan_dirs(vec!["src/api/v1".into()])`.

   The scanner reads every `.rs` file in `src/api/v1/` (excluding the `generated/` subdirectory) and extracts function signatures.

4. ### Build

   ```bash
   cargo build
   ```

   The scanner parses your new file, extracts `recent_count` and `personal_best`, classifies them, and includes them in `ApiOutput`. Downstream generators produce handlers for them.

5. ### Check the generated transports

   After the build, look at your generated transport files. Your custom functions should appear alongside the CRUD handlers.

   **HTTP routes**: `recent_count` becomes a `GET` endpoint (no body parameter, classified as `CustomGet`). `personal_best` is also `GET` because its first parameter (`exercise_id: i64`) is an id-like primitive that fits in a URL path segment.

   **IPC commands**: both functions get `#[tauri::command]` wrappers.

   **MCP tools**: both get tool definitions with your doc comments as descriptions.

</Steps>

## Function classification rules

The scanner classifies each function into an `OpKind` that drives HTTP verb and route structure. Classification first looks at the function name (matches against the CRUD vocabulary and the junction-table conventions); for custom functions that don't match a vocabulary entry, the classifier consults the first user-facing parameter's type to pick `CustomGet` vs `CustomPost`.

### CRUD and junction vocabulary

The CRUD rows are served as JSON:API resources when the module is backed by a schema entity; see [Server Transports](/guides/server-transports/#httpaxum-generation). Custom operations, junction operations and the CRUD functions of a module with no entity behind it are served as custom ops: arguments go in `meta.args` (`POST`, `PATCH`) or `opArg[name]` (`GET`), and the result comes back under `meta.result`. In such a module `update` is a `PATCH` like everywhere else. See [Operations that are not CRUD](/guides/server-transports/#operations-that-are-not-crud).

| Function name | `OpKind` | HTTP | Route example |
|---------------|----------|------|---------------|
| `list` | `List` | `GET` | `/api/workouts` |
| `get_by_id` | `GetById` | `GET` | `/api/workouts/{id}` |
| `create` | `Create` | `POST` | `/api/workouts` |
| `update` | `Update` | `PATCH` | `/api/workouts/{id}` |
| `delete` | `Delete` | `DELETE` | `/api/workouts/{id}` |
| `add_{child}(parent_id, child_id)` | `JunctionAdd` | `POST` | `/api/workouts/{parent_id}/{child}` |
| `remove_{child}(parent_id, child_id)` | `JunctionRemove` | `DELETE` | `/api/workouts/{parent_id}/{child}/{child_id}` |
| `list_{children}(parent_id)` | `JunctionList` | `GET` | `/api/workouts/{parent_id}/{children}` |

### Custom functions (CustomGet / CustomPost)

For names that don't match a vocabulary entry, the classifier looks at the function name and the *shape* of the first user-facing parameter:

| Function shape | `OpKind` | HTTP | How parameters are extracted |
|----------------|----------|------|------------------------------|
| Zero user-facing parameters, name starts with a read prefix | `CustomGet` | `GET` | (no extraction) |
| Zero user-facing parameters, any other name | `CustomPost` | `POST` | (no extraction) |
| `get_{name}(state, id: &str)` (or `String`, integer, `Uuid`, …) | `CustomGet` | `GET` | First param → URL path segment (`/api/.../{id}`) |
| `get_{name}(state, q: Option<…>)` | `CustomGet` | `GET` | `Option<…>` params → `opArg[q]` query parameters |
| `get_{name}(state, body: &CustomStruct)` | `CustomPost` | `POST` | Body-carrying first param → `meta.args.body` |
| Any other shape | `CustomPost` | `POST` | Every param after the state, `*Input` and `Option<…>` included → `meta.args` in the body |
| Returns `tokio::sync::broadcast::Receiver<T>` (or `Result<Receiver<T>, E>`) | `EventStream` | `GET` (SSE) | `/api/events/{event-name}`; required params → path segments, `Option<…>` → query, `resume` ← `Last-Event-ID` |

<Aside type="caution" title="Zero-param functions default to POST">
A function with no user-facing parameters carries no body, but that doesn't make it a read -- `pause(state)`, `backup(state)`, and `reset_all(state)` all mutate state with no params. Per RFC 7231 §4.2.1, GET must be safe, so the classifier defaults these to `CustomPost`.

It opts back into `CustomGet` only when the name starts with one of the **known read prefixes**:

```text
get_   list_   count_   exists_   find_   is_   has_
```

So `get_status(state)` emits `GET`, and `refresh_cache(state)` emits `POST`. Override either direction with [`#[ontogen::http::get]` or `#[ontogen::http::post]`](#forcing-a-method).
</Aside>

The id-like primitive allowlist is: `bool`, `char`, `i8`–`i128`, `isize`, `u8`–`u128`, `usize`, `f32`, `f64`, `String`, `str`, and `Uuid`. References to any of these (`&str`, `&String`) are also path-extractable. Anything else (a single-segment custom struct, a fully-qualified path like `crate::schema::Foo`, or a generic container like `Vec<T>` / `HashMap<K, V>`) is treated as body-carrying.

For custom functions, the module name becomes part of the route path. The function name is kebab-cased for the URL segment.

<Aside type="tip">
**`get_*` with a body.** A function named `get_filtered_sessions(store, filter: &ExportFilterRequest)` reads as a "get" semantically, but the filter is too complex to fit in a URL. Classification handles this automatically: because `ExportFilterRequest` is a custom struct, the function emits a `POST /api/{module}/filtered-sessions` route with the filter as the JSON body. The HTTP method is `POST` but the operation remains read-only on the IPC and MCP sides (those transports don't distinguish GET from POST).

If you need to force a method regardless of name or param shape, use the source-side `#[ontogen::http::post]` / `#[ontogen::http::get]` attributes -- see [Forcing a method](#forcing-a-method) below.
</Aside>

### Errors from custom endpoints

A custom endpoint's success body is unchanged, but its errors are not. A failure from a generated route, custom ones included, is a JSON:API error document (`application/vnd.api+json`, an `errors` array with one object). If the function returns your `AppError`, the variant decides the status and `code` through the same suffix rule as the CRUD routes (`*NotFound` 404, `*IdRequired` 400, `*AlreadyExists` 409, `*ParentRequired` 403, otherwise 500, `code` the variant name in snake_case); `detail` is the error's `Display` text. A function whose error type is not `AppError` answers `500 internal_error`. "Your `AppError`" means `{types_import_path}::AppError`, read through the file's `use` items; one reached by another path (a re-export such as `crate::schema::error::AppError`, or a type alias) is not recognized, answers `500 internal_error`, and a type named `AppError` there gets a build warning. A malformed query parameter, or a method the route does not serve (`405` with `Allow`), is also an `errors` document. The scan reads `ServersConfig::error_source_dir`; see the [upgrade notes](/reference/upgrading/#apperror).

## Recipe: Filtered lists

The store takes no filter, so a filtered list is hand-written. Put it in the module named after the entity, and it replaces the generated `list`. This recipe assumes the module is paginated: it is named in `.api_paginated(..)` and its surface sets `pagination` (here `PaginationConfig { default_limit: 20, max_limit: 100 }`, as in the tasks-tracker example), so the `list` takes `limit` and `offset` and has a `count` beside it:

```rust
// src/api/v1/task.rs

pub use super::generated::task::*;

use schemars::JsonSchema;
use serde::{Deserialize, Serialize};

use crate::schema::{AppError, Task};
use crate::store::Store;

#[derive(Debug, Clone, Default, Deserialize, Serialize, JsonSchema)]
pub struct ListTasksQuery {
    pub status: Option<String>,
    pub epic_id: Option<String>,
}

fn matches(task: &Task, query: &ListTasksQuery) -> bool {
    query.status.as_deref().is_none_or(|s| task.status == s)
        && query.epic_id.as_deref().is_none_or(|e| task.epic_id.as_deref() == Some(e))
}

/// List tasks, optionally filtered by status and epic
pub async fn list(
    store: &Store,
    query: ListTasksQuery,
    limit: Option<u64>,
    offset: Option<u64>,
) -> Result<Vec<Task>, AppError> {
    let tasks = store.list_tasks(None, None).await?;
    Ok(tasks
        .into_iter()
        .filter(|t| matches(t, &query))
        .skip(offset.unwrap_or(0) as usize)
        .take(limit.map_or(usize::MAX, |l| l as usize))
        .collect())
}

/// Count the tasks the same filter selects
pub async fn count(store: &Store, query: ListTasksQuery) -> Result<u64, AppError> {
    let tasks = store.list_tasks(None, None).await?;
    Ok(tasks.iter().filter(|t| matches(t, &query)).count() as u64)
}
```

- **`pub use super::generated::task::*;`** keeps `get_by_id`, `create`, `update` and `delete` available from the same module. The hand-written `list` and `count` take precedence over the generated ones of the same name.
- **A paginated module needs its own `count`.** A hand-written `list` drops the generated `count`, because the generated one counts the whole table, so the total would be wrong. Without a `count` that takes the same filter, the build fails.
- **Re-export the query struct from `types_import_path`.** The generated handlers import every type an API function names from that path, so with `types_import_path: "crate::schema"` add `pub use crate::api::v1::task::ListTasksQuery;` to `src/schema/mod.rs` (or define the struct there).
- **The query struct** is taken by value, and at most one is allowed per list. The MCP generator parses it from the tool arguments with `serde_json::from_value(..).unwrap_or_default()` and publishes its schema, so it needs `Deserialize`, `Default` and `JsonSchema`; the IPC and MCP list handlers clone it into `list`, so it needs `Clone`.
- **Bare parameters** work too: `list(store, skill_id: &str, limit, offset)` is `filter[skill_id]`, required unless it is an `Option`. A bare parameter's type must be one a single value can carry (`&str`, `String`, numbers, `bool`, unit enums). An `*Input` parameter on a `list` is refused.
- **Without an entity.** A `list` in a module with no entity behind it is a custom op at `GET /api/{module}`, with `filter[...]` and `opArg[limit]`/`opArg[offset]`, answering `meta.result`.

Over HTTP the list above answers:

```http
GET /api/tasks?filter[status]=closed/done&filter[epic_id]=markdown-backend
```

```json
{
  "jsonapi": { "version": "1.1" },
  "links": {
    "self":  "/api/tasks?filter%5Bepic_id%5D=markdown-backend&filter%5Bstatus%5D=closed%2Fdone&page%5Boffset%5D=0&page%5Blimit%5D=20",
    "first": "/api/tasks?filter%5Bepic_id%5D=markdown-backend&filter%5Bstatus%5D=closed%2Fdone&page%5Boffset%5D=0&page%5Blimit%5D=20",
    "prev":  null,
    "next":  null,
    "last":  "/api/tasks?filter%5Bepic_id%5D=markdown-backend&filter%5Bstatus%5D=closed%2Fdone&page%5Boffset%5D=0&page%5Blimit%5D=20"
  },
  "meta": { "total": 1, "limit": 20, "offset": 0 },
  "data": [ … ]
}
```

`meta.total` is `count` with the same filter.

In an unpaginated module the `list` takes no `limit` or `offset` and needs no `count`. It answers every matching task in `data`, with no `meta` and no pagination links; `links.self` carries the filter, e.g. `/api/tasks?filter%5Bstatus%5D=closed%2Fdone`.

An unknown member (`filter[colour]`), a repeated one, or a value the struct rejects is `400 invalid_query_parameter`. The generated TypeScript client keeps its signature, `taskList(query?, limit?, offset?)`, and sends `filter[...]`. See the [upgrade notes](/reference/upgrading/#filtered-lists) for the full list of errors.

## Organizing custom endpoints

There's no enforced file structure -- the scanner just reads `.rs` files from your scan directories. But here are patterns that work well:

**Per-entity custom operations**: put them in a file named after the entity (not in `generated/`):

```
src/api/v1/
  generated/          # ontogen writes here
    workout.rs        # list, get_by_id, create, update, delete
  workout.rs          # your custom workout operations (archive, duplicate)
  mod.rs
```

**Cross-entity operations**: use a descriptive module name:

```
src/api/v1/
  generated/
  reports.rs          # functions that query across multiple entities
  import_export.rs    # bulk import/export operations
  mod.rs
```

**Domain-specific modules**: group by business function:

```
src/api/v1/
  generated/
  training_plans.rs   # training plan operations
  progress.rs         # progress tracking queries
  mod.rs
```

<Aside type="tip">
The scanner skips `mod.rs` and `generated/` subdirectories automatically. Everything else in your scan directory is fair game.
</Aside>

## Writing scannable functions

For the scanner to pick up your function correctly, follow these conventions:

**First parameter must be the state or store type:**

```rust
// Store-scoped (entity operations)
pub async fn archive(store: &Store, id: &str) -> Result<(), AppError> { ... }

// AppState-scoped (app-level operations)
pub async fn health_check(state: &AppState) -> Result<String, AppError> { ... }
```

The parser accepts the function when the rendered first-parameter type contains your configured `state_type` or `store_type` as a substring. `&AppState`, `&Arc<AppState>`, and `State<'_, Arc<AppState>>` all match `state_type = "AppState"`. See [Service functions: accepted signatures](/guides/api-layer/#service-functions-accepted-signatures) for the full table including edge cases.

<Aside type="caution">
A `pub fn` whose first parameter doesn't match — or that takes `&self`, or has no parameters at all — used to be silently dropped. The build now emits a `cargo:warning=` per dropped function so you find out before clients fail to compile. If you don't see your function in the generated transports, check the `cargo build` output.
</Aside>

**Return type must be `Result<T, AppError>`** (or whatever your error type is):

```rust
pub async fn count(store: &Store) -> Result<i64, AppError> { ... }
```

**Parameters after the state/store are extracted as route params or query params:**

```rust
// `id` becomes a path parameter: GET /api/workouts/sets/{id}
pub async fn get_sets(store: &Store, id: &str) -> Result<Vec<WorkoutSet>, AppError> { ... }

// `input` becomes `meta.args.input`: POST /api/workouts/import
pub async fn import(store: &Store, input: ImportWorkoutsInput) -> Result<Vec<Workout>, AppError> { ... }
```

You can take parameters by reference (`&str`, `&[u8]`, `&Path`, `&CStr`, `&OsStr`, `&MyStruct`) or wrap them in `Option<…>`. The generator declares the matching sized owned type in the handler and forwards the borrow back to your function. See [Parameter types: references and `Option` shapes](/guides/api-layer/#parameter-types-references-and-option-shapes) for the full table.

**Use doc comments for descriptions:**

```rust
/// Archive a workout. Archived workouts are hidden from the default list
/// but can be restored later.
pub async fn archive(store: &Store, id: &str) -> Result<(), AppError> { ... }
```

**Opt out of the state-first-param rule with `#[ontogen::stateless]`:**

Some operations genuinely don't need state — clock reads, pure data transforms, OS-level side effects. Mark them with `#[ontogen::stateless]` and the parser will accept any (or no) first parameter, while the generators emit handlers without the `State<...>` extractor:

```rust
use ontogen::stateless;

// Zero params — handler is `fn util_now() -> Result<i64, String>`
#[stateless]
pub fn now() -> Result<i64, AppError> {
    Ok(chrono::Utc::now().timestamp())
}

// Non-state first param — handler signature is just `text: String`
#[stateless]
pub fn copy(text: &str) -> Result<(), AppError> {
    clipboard::copy_text(text.to_string()).map_err(AppError::DbError)
}
```

See [Stateless utility functions](/guides/api-layer/#stateless-utility-functions-ontogenstateless) for the full behaviour.

### Forcing a method

Two attributes override classification outright, for the cases where the name-and-shape heuristic reads a handler wrong.

**`#[ontogen::http::post]`** — for a mutating handler the classifier would route as a read. The usual case is a read-prefixed name that isn't a read:

```rust
use ontogen::http::post;

// `get_fresh_token` starts with `get_`, so it would classify as GET.
// It mints a token — that's a mutation.
#[post]
pub async fn get_fresh_token(state: &AppState) -> Result<String, AppError> {
    state.auth.mint().await
}
```

**`#[ontogen::http::get]`** — for a read the classifier would route as `POST`. This is the escape hatch for an asymmetry in the name heuristic: the read-prefix allowlist is consulted **only** for functions with no user-facing params, and among functions that *do* carry params only `get_` has a branch back into `CustomGet`. So a read with arguments named `count_*`, `exists_*`, `find_*`, `is_*`, or `has_*` classifies `CustomPost` however side-effect-free it is:

```rust
use ontogen::http::get;

// Has a param and isn't named `get_*`, so it would classify as POST.
#[get]
pub async fn count_matching(store: &Store, pattern: &str) -> Result<i64, AppError> {
    store.count_matching(pattern).await
}
```

Before this attribute existed the only remedy was renaming to `get_*`, which bends a handler's name to satisfy the router rather than to describe what it does.

Both overrides **win outright**. Forcing GET is you asserting the param shape suits a GET; it deliberately does not re-run the body-carrying-first-param check that the `get_*` branch applies. An override that second-guesses the author isn't an override.

<Aside type="note">
These attributes live under the `http::*` namespace because the override is specifically HTTP-method-shape; routing-shape-agnostic attributes (`stateless`, `rename`, `skip`) stay at the top of the `ontogen::` namespace.

The parser matches on the **final path segment**, so `#[ontogen::http::get]`, a bare `#[get]` after a `use ontogen::http::get;`, and any other path ending in `::get` all work. The macros themselves are no-ops; the ontogen parser reads them via `syn` during build-time scanning and stamps `ApiFn::force_method`, which `classify_op` short-circuits on.
</Aside>

Combine freely with `#[ontogen::stateless]` and `#[ontogen(rename = "…")]` — order doesn't matter, the parser inspects each attribute independently.

## Rerun directives

Don't forget to set up `cargo:rerun-if-changed` for your custom API directory. In your `build.rs`:

```rust
ontogen::emit_rerun_directives_excluding(
    &PathBuf::from("src/api/v1"),
    &["generated"],
);
```

This watches all files in `src/api/v1/` except the `generated/` subdirectory. When you edit a custom endpoint, Cargo re-runs the build script and the scanner picks up your changes.

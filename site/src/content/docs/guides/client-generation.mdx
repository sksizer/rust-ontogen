Ontogen generates TypeScript client code that mirrors your server API surface. Three client generators cover different deployment scenarios: a pure HTTP client, a split transport that switches between HTTP and Tauri IPC at runtime, and an admin registry that provides per-entity metadata for admin UIs.

## Client generator variants

Client generators are configured through the `generators` field on `ClientsConfig` and run by `gen_clients` (or, more commonly, `Pipeline::clients(...).build()`):

```rust
use ontogen::clients::ClientGenerator;
use ontogen::ClientsConfig;

let clients_config = ClientsConfig {
    // ... api_dir, state_type, naming, etc.
    generators: vec![
        ClientGenerator::HttpTs {
            output: "../src-nuxt/app/types/httpCommands.ts".into(),
            bindings_path: "../src-nuxt/app/types/bindings.ts".into(),
        },
        ClientGenerator::HttpTauriIpcSplit {
            output: "../src-nuxt/app/transport/generated.ts".into(),
            bindings_path: "../src-nuxt/app/types/bindings.ts".into(),
        },
        ClientGenerator::AdminRegistry {
            output: "../src-nuxt/layers/admin/generated/admin-registry.ts".into(),
        },
    ],
    // ...
    extra_surfaces: vec![],
};
```

<Aside type="note">
  `gen_clients` is a sibling of `gen_servers`, and like it takes the parsed schema as its first argument. Server-side transport generation (Axum / Tauri IPC / MCP) and client-side TypeScript generation no longer share a config struct; each has its own dedicated entry point and config type.
</Aside>

`ClientGenerator` lives at `ontogen::clients::ClientGenerator` (re-exported at the module level). The internal path `ontogen::clients::config::ClientGenerator` is `pub(crate)` and no longer accessible to downstream crates.

## Formatting the output

Ontogen does not format the TypeScript it generates. `ClientsConfig::ts_formatter` defaults to `TsFormatter::None`, which writes each file exactly as the generators produced it.

That's usually what you want when the consuming project runs its own formatter over the tree. If you'd rather the generated files land already matching your style:

```rust
// Shell out to an external formatter. The output file's resolved path is
// appended as the final argument, so prettier can resolve its own config.
// Runs from the nearest ancestor node_modules directory when one exists.
ts_formatter: ontogen::TsFormatter::Command(vec![
    "prettier".into(),
    "--stdin-filepath".into(),
]),

// Or format in-process with a library of your choice.
ts_formatter: ontogen::TsFormatter::custom(|src, _path| {
    my_formatter::format(src).map_err(|e| e.to_string())
}),
```

`TsFormatter::custom` fails the build if the hook returns `Err`. `TsFormatter::custom_with(f, OnFormatError::…)` lets you pick a laxer policy for cases where formatting is nice-to-have but shouldn't be able to break codegen.

<Aside type="note">
Whatever formatter you configure runs **in memory, before** the write-if-changed comparison. So a rebuild that produces identical formatted output touches no files and trips no watchers -- the same property [`rustfmt`](/concepts/design-philosophy/) gives the Rust side.
</Aside>

## TypeScript HTTP client

The `HttpTs` generator produces a typed, fetch-based HTTP client. For each API function, it generates a TypeScript function that makes the appropriate HTTP request.

The server speaks JSON:API for CRUD routes (see [Server Transports](/guides/server-transports/#httpaxum-generation)), and the client hides that. The functions keep their flat signatures: entities go in and come out as plain objects with the schema's field names, `null` for cleared optionals and id arrays for relations. The client turns each resource object into a flat entity (`flattenTask`: the id under the entity's own id field name, then `attributes`, then relationships as `epic_id` or a `tags` id array) and turns flat inputs back into `{ data: { type, id?, attributes, relationships } }` request bodies (`unflattenTask`). Each entity's resource type, id field and relationships come from a generated per-entity resource table.

```typescript
// Auto-generated HTTP client. DO NOT EDIT.

import type {
  Task,
  CreateTaskInput,
  UpdateTaskInput,
} from './bindings';

export async function taskList(): Promise<Task[]> {
  // GET /api/tasks, then data.map(flattenTask)
}

export async function taskGetById(id: string): Promise<Task> {
  // GET /api/tasks/{id}, then flattenTask(data)
}

export async function taskCreate(input: CreateTaskInput): Promise<Task> {
  // POST /api/tasks with unflattenTask(input), then flattenTask(data)
}

export async function taskUpdate(id: string, input: UpdateTaskInput): Promise<Task> {
  // PATCH /api/tasks/{id} with unflattenTask(input, id), then flattenTask(data)
}

export async function taskDelete(id: string): Promise<null> {
  // DELETE /api/tasks/{id}, resolves null on 204
}
```

Function names follow the same entity-first convention as the server transports: `taskList`, `taskGetById`, `taskCreate`. The naming is camelCase for TypeScript conventions.

On the wire:

- Every request sends `Accept: application/vnd.api+json`. Requests with a body send `Content-Type: application/vnd.api+json`.
- Updates use `PATCH` (`httpPatch`). No generated route uses `PUT`, so there is no `httpPut` helper.
- A key whose value is `undefined` is left out of an update body, which means "unchanged". `null` is sent and clears the field. A relation field moves into `relationships`; every other key goes in `attributes`. The id goes in `data.id`, never in `attributes`.
- A paginated list in the `HttpTauriIpcSplit` HTTP transport sends `page[offset]` and `page[limit]` and still returns `PaginatedResult<T>` (`items`, `total`, `limit`, `offset`), built from `data` and `meta`. `limit` and `offset` are the effective values the server used. The HTTP-only client (`HttpTs`) pages the same way: its paginated list methods take `limit?` and `offset?` and return `PaginatedResult<T>`.
- `include` is not exposed on the TS transport. It is an HTTP-only query parameter, and the flat return shape (entities, `PaginatedResult<T>`) has nowhere to put `included` resources; call the route directly to use it.
- A filtered list sends the `filter[...]` family: `toQueryString({ filter: query, page: { offset, limit } })` for a query struct, `{ skill_id: skillId }` for bare parameters, and `{ ...query, skill_id: skillId }` for both. A filtered list with no entity behind it sends `filter[...]` with `opArg[limit]` and `opArg[offset]`. The method signatures are unchanged: bare parameters, then `query?`, then `limit?` and `offset?`.

### Errors

Any non-2xx response, from a CRUD route or any other generated route, throws a `JsonApiError` (the file also exports `JsonApiErrorObject` and `JsonApiResource`):

```typescript
class JsonApiError extends Error {
  readonly status: number;
  readonly errors: JsonApiErrorObject[]; // [] when the body was not a JSON:API error document
}
```

`message` is the first error's `detail` (or its `title`, or the status text), the same text the server sent before. `String(e)` now reads `JsonApiError: Task not found: nope` where it used to read `Error: Task not found: nope`. Read `e.status` and `e.errors[0]?.code` when you need to branch on the failure. A non-JSON body, such as a proxy's HTML `502`, still throws a `JsonApiError` with an empty `errors`.

Custom endpoints discovered through API scanning get client functions too. They follow the custom op wire: a `POST` sends its arguments as `{ meta: { args: { … } } }` (no body when there are none), a `GET` sends `Option` arguments as `opArg[name]`, and every call resolves to the response's `meta.result` (`null` on `204`). The same holds for the junction and CRUD methods of a module with no entity behind it, and for a lone `list_X` (one with no `add_Y` or `remove_Y` beside it), which is a custom `GET` and returns its plain array. Entity-less lists and the junction lists of such a module page with `opArg[limit]` and `opArg[offset]` and still return `PaginatedResult<T>`.

Junction methods of a module named after an entity call its [relationship endpoints](/guides/server-transports/#relationship-endpoints), with the same signatures: `taskListLabels(taskId)` reads `GET /api/tasks/{taskId}/labels` and flattens each resource (a list of ids reads `…/relationships/labels` and maps each identifier to its id), and on a paginated surface takes `limit?` and `offset?`, sends `page[…]` and returns `PaginatedResult<T>`. `taskAddLabel(taskId, tagId)` and `taskRemoveLabel(taskId, tagId)` send `POST` and `DELETE /api/tasks/{taskId}/relationships/labels` with `{ data: [{ type: 'tags', id: tagId }] }` and resolve `null`. With a route prefix, the split transport calls the same paths under the prefix. Subscriptions hand the callback a flat entity for an entity item and the `meta.result` value for any other item. `HttpTs` calls the server's own paths, kebab-cased and singleton-aware.

```typescript
export async function taskGetOverdue(): Promise<Task[]> {
  // GET /api/tasks/overdue
}
```

### The bindings_path option

The `bindings_path` points to the TypeScript file that holds the type definitions the client imports. **Ontogen owns this file** -- on every build it rewrites the path with a fresh set of TS aliases. Two emitters cooperate to populate it:

- **Schema-known emitter** -- entity types from `src/schema/` plus the `Create{Entity}Input` / `Update{Entity}Input` DTOs Ontogen derives are emitted directly from `EntityDef` via a bounded mapping over `FieldType`. No user setup required.
- **Long-tail emitter** -- user-owned types referenced by a custom API endpoint's input or return type (anything that isn't an entity or a generated DTO) are emitted by the [`ontogen-ts`](https://docs.rs/ontogen-ts) crate. A build-time AST walker scans your `src/` for the reachable closure of every long-tail type and appends the result to `bindings_path`.

The long-tail emitter runs entirely inside `build.rs`. There is no separate compilation, no extra binary, no `cargo` invocation, no `CARGO_TARGET_DIR` isolation. The walker reads `.rs` files with [`syn`](https://docs.rs/syn) and emits TypeScript directly from the AST.

You don't need to opt long-tail types in -- the walker discovers them automatically from your API signatures and recursively pulls in everything they reference. If a referenced type lives in a workspace-sibling crate, declare the sibling's source root in `pool_extra_roots`; see the [TypeScript bindings guide](/guides/typescript-bindings/#workspace-sibling-types).

If a type's shape isn't in the supported subset, or a serde attribute isn't recognized, or a reference can't be resolved, the build hard-errors with the full punch-list. See the [error model](/guides/typescript-bindings/#error-model) for the four variants and how to handle each.

<Aside type="caution">
  `bindings_path` is an **output**, not an input. Any pre-existing manual `specta::export_ts!` binary that wrote to the same file should be deleted -- Ontogen overwrites it on every build.
</Aside>

For the full ontogen-ts story -- supported subset, serde rename family, BigInt rendering, external types, the `#[ontogen::ts_opaque]` / `#[ontogen::ts_name]` escape hatches -- see the dedicated [TypeScript bindings guide](/guides/typescript-bindings/).

## Split transport (HTTP + Tauri IPC)

The `HttpTauriIpcSplit` generator is for applications that run as both a web app and a Tauri desktop app. It generates a `Transport` interface with two implementations:

```typescript
interface Transport {
  taskList(): Promise<Task[]>;
  taskGetById(id: string): Promise<Task>;
  taskCreate(input: CreateTaskInput): Promise<Task>;
  // ... all operations
}

function createHttpTransport(): Transport {
  return {
    taskList: () => /* GET /api/tasks, flattened */,
    taskGetById: (id) => /* GET /api/tasks/{id}, flattened */,
    taskCreate: (input) => /* POST /api/tasks, flattened */,
    // ...
  };
}

function createIpcTransport(): Transport {
  return {
    taskList: () => invoke('task_list'),
    taskGetById: (id) => invoke('task_get_by_id', { id }),
    taskCreate: (input) => invoke('task_create', { input }),
    // ...
  };
}
```

At runtime, you detect the environment and pick the right transport:

```typescript
const transport = window.__TAURI__
  ? createIpcTransport()
  : createHttpTransport();
```

Both implementations have identical signatures, and the IPC payloads are flat as before; JSON:API applies to the HTTP transport only. Code that uses the transport doesn't know or care whether it's talking to a local server over HTTP or to the Tauri backend over IPC.

### Event subscriptions

Each event op gets a `subscribeX(args, handlers)` method on the `Transport` interface and both implementations:

```typescript
subscribeVaultNoteChanges(
  args: { vaultId: string; classes?: string | null; resume?: string | null },
  handlers: SubscriptionHandlers<LoggedChange>,
): Promise<() => void>; // resolves to the unsubscribe function

interface SubscriptionHandlers<T> {
  onEvent: (data: T, id: string | null) => void;
  onLag?: (skipped: number) => void;
  onOpen?: () => void; // first connect and every reconnect
  onError?: (err: unknown) => void;
}
```

- **HTTP** opens an `EventSource` on the event's SSE route. On an error it closes, waits a capped exponential backoff with jitter (0.5 s doubling to 30 s), and reconnects with the last seen id as the `resume` query param. An initial `args.resume` starts from that id.
- **IPC** calls `{fn}_subscribe` with a new Tauri `Channel`; the returned function calls `{fn}_unsubscribe`.
- `onLag` fires when the server dropped events for this subscriber. `onOpen` fires on every (re)connect. Together they are where a consumer runs its own catch-up read; the generated client does no domain catch-up.

Parameterless sync event ops also keep the older `onX(callback)` methods, which carry untyped payloads and do not report lag.

### Route prefix in client code

Route prefixes apply to the `HttpTauriIpcSplit` transport only; the `HttpTs` client does not support them, so against a server generated with a route prefix its calls do not reach the scoped routes. When `route_prefix` is configured, the split transport's functions accept an optional project ID parameter:

```typescript
export async function taskList(projectId?: string): Promise<Task[]> {
  const prefix = projectId ? `/projects/${projectId}` : '';
  // GET /api/projects/{projectId}/tasks, flattened
}
```

For the IPC transport, the project ID is passed as an additional argument to `invoke`:

```typescript
taskList: (projectId) => invoke('task_list', {
  projectId: projectId ?? null
}),
```

## Admin registry

The `AdminRegistry` generator produces a TypeScript file with per-entity metadata for admin UIs. This is designed for generic admin interfaces that can render CRUD forms and tables without hand-written configuration.

```typescript
// Auto-generated admin registry. DO NOT EDIT.

import type { AdminFieldDef, AdminEntityConfig } from '@ontogen/admin-types'

export const adminEntities: AdminEntityConfig[] = [
  {
    key: 'task',
    plural: 'tasks',
    label: 'Task',
    pluralLabel: 'Tasks',
    idType: 'string',
    listMethod: 'taskList',
    getMethod: 'taskGetById',
    createMethod: 'taskCreate',
    updateMethod: 'taskUpdate',
    deleteMethod: 'taskDelete',
    returnType: 'Task',
    createInputType: 'CreateTaskInput',
    updateInputType: 'UpdateTaskInput',
    paginated: false,
    fields: [
      { key: 'name', label: 'Name', type: 'string', role: 'plain', required: true },
      { key: 'status', label: 'Status', type: 'string', role: 'enum', required: false },
      { key: 'assignee_id', label: 'Assignee', type: 'string', role: 'relation',
        relation: { kind: 'belongs_to', target: 'agent' }, required: false },
    ],
  },
  // ... more entities
];
```

The registry only includes modules that have all five CRUD functions (`list`, `get_by_id`, `create`, `update`, `delete`). Partial or custom-only modules are excluded.

### Per-field metadata

When `gen_clients` is given the parsed schema (the `Pipeline` builder passes it from the schema stage), the admin generator emits detailed field information:

- **type** -- the TypeScript type (`string`, `number`, `boolean`, arrays)
- **role** -- the field's purpose (`id`, `plain`, `enum`, `relation`, `body`)
- **relation metadata** -- for relation fields, the kind (`belongs_to`, `has_many`, `many_to_many`) and target entity
- **required** -- whether the field is required vs optional

This lets admin UI frameworks render appropriate input components (text fields, dropdowns, relation pickers) without per-entity configuration.

### Pagination metadata

When `pagination` is configured, each entity config includes pagination details:

```typescript
{
    paginated: true,
    defaultLimit: 50,
    maxLimit: 200,
    // ...
}
```

Admin UIs can use this to render pagination controls with sensible defaults. The registry flags are unchanged; the HTTP transport maps them to `page[offset]` and `page[limit]`.

## ts_skip_commands

Some IPC commands shouldn't appear in the TypeScript client -- perhaps they're internal or handled through a different mechanism. The `ts_skip_commands` list on `ClientsConfig` excludes specific commands by their canonical name:

```rust
ts_skip_commands: vec![
    "system_health_check".to_string(),
    "internal_reindex".to_string(),
],
```

Skipped commands are omitted from both the HTTP client and the split transport. They still get server-side handlers (those are controlled by `ServersConfig`, which has its own dispatch).

## How client functions mirror the server API

The client generators discover functions through the same `ApiModule` list that the server generators use. For each function, the generator:

1. Determines the HTTP method and path from `OpKind`.
2. Renders Rust parameter and return types to TypeScript through [`ontogen_ts::render_type_str`](/guides/typescript-bindings/#rendering-a-single-type) -- the same classifier that emits `bindings.ts`, so a parameter's type in the client always matches the same type in the bindings.
3. Checks which TypeScript types are available in `bindings.ts`.
4. Generates a function with matching name, parameters, and return type.

This means custom API endpoints you add through `scan_dirs` automatically get client functions too. You write the Rust function, rebuild, and the TypeScript client has a new typed function ready to call.

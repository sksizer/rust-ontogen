Your `build.rs` is where the Ontogen pipeline runs. There are two ways to wire it up: the `Pipeline` builder (recommended for almost everything) and direct calls to the underlying generator functions (when you need maximum control).

## The recommended shape: `Pipeline`

`Pipeline` is a fluent builder over the generator functions. It applies sensible defaults, threads each stage's typed output into the next, and -- importantly -- forwards `schema.entities` into the admin-registry generator automatically. Method order on the builder is irrelevant; `build()` always runs stages in the canonical dependency order.

The canonical reference for a Pipeline-based `build.rs` is `examples/iron-log/src-tauri/build.rs` in the repo. Here is essentially that file:

```rust
// build.rs
use std::path::PathBuf;

use ontogen::clients::ClientGenerator;
use ontogen::servers::{NamingConfig, ServerGenerator};
use ontogen::{ClientsConfig, Pipeline, ServersConfig};

fn main() {
    println!("cargo:rerun-if-changed=build.rs");
    ontogen::emit_rerun_directives_excluding(
        &PathBuf::from("src/api/v1"),
        &["generated"],
    );

    let servers_config = ServersConfig {
        api_dir: "src/api/v1".into(),
        state_type: "AppState".into(),
        service_import_path: "crate::api::v1".into(),
        types_import_path: "crate::schema".into(),
        state_import: "crate::AppState".into(),
        naming: NamingConfig::default(),
        generators: vec![
            ServerGenerator::HttpAxum {
                output: "src/api/transport/http/generated.rs".into(),
            },
            ServerGenerator::TauriIpc {
                output: "src/api/transport/ipc/generated.rs".into(),
            },
        ],
        rustfmt_edition: "2024".into(),
        sse_route_overrides: Default::default(),
        route_prefix: None,
        store_type: Some("Store".into()),
        store_import: Some("crate::store::Store".into()),
        pagination: None,
    };

    let clients_config = ClientsConfig {
        api_dir: "src/api/v1".into(),
        state_type: "AppState".into(),
        service_import_path: "crate::api::v1".into(),
        types_import_path: "crate::schema".into(),
        state_import: "crate::AppState".into(),
        naming: NamingConfig::default(),
        generators: vec![
            ClientGenerator::HttpTauriIpcSplit {
                output: "../src-nuxt/app/generated/transport.ts".into(),
                bindings_path: "../src-nuxt/app/generated/types.ts".into(),
            },
            ClientGenerator::AdminRegistry {
                output: "../src-nuxt/app/admin/generated/admin-registry.ts".into(),
            },
        ],
        // Generated TS is emitted as-is unless you set a formatter here.
        ts_formatter: ontogen::TsFormatter::None,
        sse_route_overrides: Default::default(),
        ts_skip_commands: vec![],
        route_prefix: None,
        store_type: Some("Store".into()),
        store_import: Some("crate::store::Store".into()),
        pagination: None,
        // Pipeline auto-fills these two; leave them empty.
        schema_entities: Vec::new(),
        pool_extra_roots: Vec::new(),
        pool_exclude_paths: Vec::new(),
    };

    Pipeline::new("src/schema")
        .seaorm(
            "src/persistence/db/entities/generated",
            "src/persistence/db/conversions/generated",
        )
        .dtos("src/schema/dto")
        .store("src/store/generated", Some::<PathBuf>("src/store/hooks".into()))
        .api("src/api/v1/generated", "AppState")
        .servers(servers_config)
        .clients(clients_config)
        .build()
        .unwrap_or_else(|e| {
            e.emit_cargo_warning();
            panic!("ontogen pipeline failed: {e}");
        });

    // For Tauri projects, run tauri_build::build() after Ontogen's pipeline.
}
```

That's roughly 80 lines for a full Tauri + Nuxt pipeline -- HTTP, IPC, TypeScript split client, admin registry. To skip a stage, omit its method call.

<Aside type="tip">
The builder's defaults: `schema_module_path` defaults to `ontogen::DEFAULT_SCHEMA_MODULE_PATH` (`"crate::schema"`) and propagates to both the store and API stages; when you opt into `store(...)`, the API stage's `store_type` defaults to `Some("Store")`. Override either with `.schema_module_path(...)` or `.api_store_type(Some(_))`.

`Pipeline` also fills in `ClientsConfig.schema_entities` from the schema stage and `pool_exclude_paths` from the `seaorm()` stage, which is why both are left empty above. And it **infers the store backend** when exactly one persistence stage is configured -- if you enable both `seaorm(...)` and `markdown_io(...)`, disambiguate with `.store_backend(StoreBackendChoice::Seaorm)`.
</Aside>

### Formatting the generated TypeScript

`ts_formatter` is the one field above with a behavioural default worth knowing: `TsFormatter::None` writes the TypeScript exactly as the generators produced it, with no formatting pass.

Point it at your project's formatter if you'd rather the generated files match the rest of your tree:

```rust
// Shell out. The output file's resolved path is appended as the final
// argument, so prettier can find your config. Runs from the nearest
// ancestor node_modules directory when one exists.
ts_formatter: ontogen::TsFormatter::Command(vec![
    "prettier".into(),
    "--stdin-filepath".into(),
]),

// Or format in-process with a library of your choice.
ts_formatter: ontogen::TsFormatter::custom(|src, _path| {
    my_formatter::format(src).map_err(|e| e.to_string())
}),
```

`TsFormatter::custom` fails the build if the hook errors; `TsFormatter::custom_with(f, OnFormatError::…)` lets you pick a laxer policy when formatting is nice-to-have but shouldn't be able to break codegen.

## The explicit form

If you'd rather call each generator function directly -- to inspect intermediate IRs, to insert custom logic between stages, or just to see what `Pipeline` is doing -- the same build looks like this:

```rust
// build.rs
use std::collections::HashMap;
use ontogen::CodegenError;

/// Unwrap a codegen result, emitting a cargo:warning before panicking.
fn unwrap_codegen<T>(result: Result<T, CodegenError>, stage: &str) -> T {
    result.unwrap_or_else(|e| {
        e.emit_cargo_warning();
        panic!("{stage}: {e}");
    })
}

fn main() {
    println!("cargo:rerun-if-changed=build.rs");

    // ── 1. Parse schema ──────────────────────────────────────────
    let schema = unwrap_codegen(
        ontogen::parse_schema(&ontogen::SchemaConfig {
            schema_dir: "src/schema".into(),
        }),
        "parse schema",
    );

    // ── 2. Persistence layer (independent generators) ────────────
    let seaorm = unwrap_codegen(
        ontogen::gen_seaorm(
            &schema.entities,
            &ontogen::SeaOrmConfig {
                entity_output: "src/persistence/db/entities/generated".into(),
                conversion_output: "src/persistence/db/conversions/generated".into(),
                skip_conversions: vec![],
            },
        ),
        "gen_seaorm",
    );

    unwrap_codegen(
        ontogen::gen_dtos(
            &schema.entities,
            &ontogen::DtoConfig {
                output_dir: "src/schema/dto".into(),
            },
        ),
        "gen_dtos",
    );

    // ── 3. Store layer ───────────────────────────────────────────
    // `backend` is what decides whether the emitted CRUD talks to SeaORM
    // or to a markdown vault. Here it carries the SeaOrmOutput from above.
    let _store = unwrap_codegen(
        ontogen::gen_store(
            &schema.entities,
            &ontogen::StoreConfig {
                output_dir: "src/store/generated".into(),
                hooks_dir: Some("src/store/hooks".into()),
                schema_module_path: ontogen::DEFAULT_SCHEMA_MODULE_PATH.into(),
                backend: ontogen::Backend::Seaorm(Some(seaorm)),
                wikilink_policy: None,
            },
        ),
        "gen_store",
    );

    // ── 4. API layer ─────────────────────────────────────────────
    let api = unwrap_codegen(
        ontogen::gen_api(
            &schema.entities,
            &ontogen::ApiConfig {
                output_dir: "src/api/v1/generated".into(),
                exclude: vec![],
                scan_dirs: vec!["src/api/v1".into()],
                state_type: "AppState".to_string(),
                store_type: Some("Store".to_string()),
                schema_module_path: ontogen::DEFAULT_SCHEMA_MODULE_PATH.into(),
            },
        ),
        "gen_api",
    );

    // ── 5. Server transports ─────────────────────────────────────
    let _servers = unwrap_codegen(
        ontogen::gen_servers(
            Some(&api),
            &["src/api/v1".into()],
            &ontogen::ServersConfig {
                api_dir: "src/api/v1".into(),
                state_type: "AppState".to_string(),
                service_import_path: "crate::api::v1".to_string(),
                types_import_path: "crate::schema".to_string(),
                state_import: "crate::AppState".to_string(),
                naming: ontogen::servers::NamingConfig::default(),
                generators: vec![
                    ontogen::servers::ServerGenerator::HttpAxum {
                        output: "src/api/transport/http/generated.rs".into(),
                    },
                    ontogen::servers::ServerGenerator::TauriIpc {
                        output: "src/api/transport/ipc/generated.rs".into(),
                    },
                ],
                rustfmt_edition: "2024".to_string(),
                sse_route_overrides: HashMap::new(),
                route_prefix: None,
                store_type: Some("Store".to_string()),
                store_import: Some("crate::store::Store".to_string()),
                pagination: None,
            },
        ),
        "gen_servers",
    );

    // ── 6. TypeScript clients + admin registry ───────────────────
    unwrap_codegen(
        ontogen::gen_clients(
            Some(&api),
            &["src/api/v1".into()],
            &ontogen::ClientsConfig {
                api_dir: "src/api/v1".into(),
                state_type: "AppState".to_string(),
                service_import_path: "crate::api::v1".to_string(),
                types_import_path: "crate::schema".to_string(),
                state_import: "crate::AppState".to_string(),
                naming: ontogen::servers::NamingConfig::default(),
                generators: vec![
                    ontogen::clients::ClientGenerator::HttpTauriIpcSplit {
                        output: "../src-nuxt/app/transport/generated.ts".into(),
                        bindings_path: "../src-nuxt/app/types/bindings.ts".into(),
                    },
                    ontogen::clients::ClientGenerator::AdminRegistry {
                        output: "../src-nuxt/layers/admin/generated/admin-registry.ts".into(),
                    },
                ],
                ts_formatter: ontogen::TsFormatter::None,
                sse_route_overrides: HashMap::new(),
                ts_skip_commands: vec![],
                route_prefix: None,
                store_type: Some("Store".to_string()),
                store_import: Some("crate::store::Store".to_string()),
                pagination: None,
                // Required for the admin-registry generator. Pipeline does
                // this for you; the explicit form must pass it manually,
                // otherwise admin-registry.ts ships with empty `fields: []`.
                schema_entities: schema.entities.clone(),
                pool_extra_roots: vec![],
                // Also automatic under Pipeline. Without it, the per-entity
                // `Relation` enums gen_seaorm emitted make the long-tail
                // resolver ambiguous if you have your own `Relation` type.
                pool_exclude_paths: vec![
                    "src/persistence/db/entities/generated".into(),
                ],
            },
        ),
        "gen_clients",
    );
}
```

<Aside type="caution">
Two `ClientsConfig` fields that `Pipeline` fills in for you and the explicit form must pass manually:

- **`schema_entities`** -- required if any of your generators is `AdminRegistry`. Without it the generator silently emits empty `fields: []` for every entity and the admin UI has nothing to render.
- **`pool_exclude_paths`** -- point it at your `gen_seaorm` `entity_output`. `gen_seaorm` emits a `Relation` enum per entity, so a consumer with its own `Relation` type otherwise hits an ambiguous-match abort.
</Aside>

Server-side supporting types -- `NamingConfig`, `ServerGenerator`, `RoutePrefix`, `PaginationConfig` -- live in `ontogen::servers::*` (re-exported at the module level). The client-side `ClientGenerator` lives in `ontogen::clients::*`. Both `ClientsConfig` and `ServersConfig` re-import the shared types (`NamingConfig`, `RoutePrefix`, etc.) from `ontogen::servers::*` -- a follow-up may relocate them to a shared module.

## The recommended ordering

The pipeline has a natural flow, and while generators are independent functions, the data dependencies create an ordering:

```
parse_schema  ─────────────────────────────────── required first
     │
     ├── gen_seaorm       ─── independent, returns SeaOrmOutput      ──┐
     ├── gen_markdown_io  ─── independent, returns MarkdownIoOutput  ──┤
     ├── gen_dtos         ─── independent, returns ()                  │
     │                                          StoreConfig.backend  <─┘
     └── gen_store        ─── returns StoreOutput
              │
              └── gen_api  ─── uses entities, returns ApiOutput
                       │
                       ├── gen_servers  ─── uses ApiOutput; emits Rust server
                       │                    transports (Axum, Tauri IPC, MCP)
                       │
                       └── gen_clients  ─── uses ApiOutput; emits TS bindings,
                                            HTTP / HTTP+IPC clients, and the
                                            admin-UI registry
```

`parse_schema` always comes first because every other generator needs `SchemaOutput.entities`. After that, `gen_seaorm`, `gen_markdown_io`, and `gen_dtos` are independent -- they only need the entity list.

`gen_store` is where the two persistence generators rejoin: its `StoreConfig.backend` decides which one it emits CRUD against. `Backend::Seaorm` takes the `SeaOrmOutput` as optional enrichment (pass `None` and it derives table and column names by convention); `Backend::Markdown` requires the `MarkdownIoOutput`, because the markdown emitter genuinely needs the vault layout and per-entity directory mapping.

`gen_api`, `gen_servers`, and `gen_clients` form a chain where `gen_api`'s output feeds both `gen_servers` (Rust transports) and `gen_clients` (TypeScript clients + admin registry); the latter two are siblings and run in stable order for deterministic rerun-if-changed traces. All three emit byte-identical output regardless of which store backend you picked.

## Error handling with CodegenError

Every generator returns `Result<T, CodegenError>`. The `CodegenError` enum has a variant per pipeline stage:

```rust
pub enum CodegenError {
    Schema(String),
    Persistence(String),
    Store(String),
    Api(String),
    Server(String),
    Client(String),
    /// An external tool required by the codegen pipeline is missing or failed
    /// (e.g., rustfmt, or whatever `TsFormatter::Command` points at).
    ExternalTool { tool: &'static str, detail: String },
}
```

The `emit_cargo_warning` method prints the error as a `cargo:warning` line, making it visible in your build output without digging through backtraces:

```rust
result.unwrap_or_else(|e| {
    e.emit_cargo_warning();
    panic!("{stage}: {e}");
})
```

When something goes wrong, you'll see:

```
warning: ontogen: Failed to parse src/schema/task.rs: expected `;` at line 15
```

This pattern is consistent across all generators, so the `unwrap_codegen` helper works for everything.

## The write-if-changed optimization

You might worry about unnecessary recompilation. If generated files are rewritten on every build, won't Cargo see changed mtimes and recompile everything?

Ontogen handles this internally. All generated file writes go through `write_if_changed`, which compares the new content with the existing file. If they're identical, the file isn't touched -- its mtime stays the same, and Cargo doesn't trigger a recompile.

```rust
// Internal to Ontogen -- you don't call this directly
pub fn write_if_changed(path: &Path, content: &[u8]) -> io::Result<()> {
    if path.exists() {
        let existing = fs::read(path)?;
        if existing == content {
            return Ok(()); // no change, skip write
        }
    }
    fs::write(path, content)
}
```

This means you can run the full pipeline on every build without worrying about compile-time overhead. Only files that actually change get written, and only changed files trigger downstream recompilation.

<Aside type="tip">
  `parse_schema` automatically emits `cargo:rerun-if-changed` directives for every `.rs` file in your schema directory. You only need the manual `cargo:rerun-if-changed=build.rs` line for the build script itself. Schema changes trigger rebuilds; unchanged schemas don't.
</Aside>

## Output directory conventions

Ontogen uses `generated/` subdirectories by convention:

| Generator | Typical output path |
|-----------|-------------------|
| `gen_seaorm` (entities) | `src/persistence/db/entities/generated/` |
| `gen_seaorm` (conversions) | `src/persistence/db/conversions/generated/` |
| `gen_dtos` | `src/schema/dto/` |
| `gen_store` | `src/store/generated/` |
| `gen_store` (hooks) | `src/store/hooks/` |
| `gen_api` | `src/api/v1/generated/` |
| `gen_markdown_io` | `src/persistence/markdown/generated/` |
| `gen_servers` (HTTP) | `src/api/transport/http/generated.rs` |
| `gen_servers` (IPC) | `src/api/transport/ipc/generated.rs` |
| `gen_servers` (MCP) | `src/api/transport/mcp/generated.rs` |
| `gen_clients` (TS) | `../src-nuxt/app/generated/transport.ts` |

The `generated/` convention makes it clear which files are machine-written and should never be edited by hand. Your `.gitignore` can either track or ignore these directories -- most projects track them so CI builds don't need to run code generation.

<Aside type="caution">
  Never edit files inside `generated/` directories. They're overwritten on every build. The one exception is hook files in `store/hooks/` -- those are scaffolded once and never touched again.
</Aside>

## Tips for organizing a large build.rs

As your entity count grows, the build script can get long. A few strategies help:

### Extract config into functions

```rust
fn schema_config() -> ontogen::SchemaConfig {
    ontogen::SchemaConfig {
        schema_dir: "src/schema".into(),
    }
}

fn seaorm_config() -> ontogen::SeaOrmConfig {
    ontogen::SeaOrmConfig {
        entity_output: "src/persistence/db/entities/generated".into(),
        conversion_output: "src/persistence/db/conversions/generated".into(),
        skip_conversions: vec![],
    }
}

fn servers_config() -> ontogen::ServersConfig {
    ontogen::ServersConfig {
        // ... all the fields
    }
}
```

### Gate generators behind feature flags

If some generators are only needed for certain build targets (e.g., Tauri IPC only for desktop builds):

```rust
let mut server_generators = vec![
    ontogen::servers::ServerGenerator::HttpAxum {
        output: "src/api/transport/http/generated.rs".into(),
    },
];

#[cfg(feature = "desktop")]
server_generators.push(ontogen::servers::ServerGenerator::TauriIpc {
    output: "src/api/transport/ipc/generated.rs".into(),
});
```

### Track what changed

After running the full pipeline, you can inspect the returned metadata to know what was generated:

```rust
let store = unwrap_codegen(ontogen::gen_store(/* ... */), "gen_store");

// StoreOutput tells you what was generated
for hook in &store.scaffolded_hooks {
    println!("cargo:warning=Scaffolded new hook file: {}", hook.file_path.display());
}
```

This is useful for first-time setup: you'll see which hook files were created and need your attention.
